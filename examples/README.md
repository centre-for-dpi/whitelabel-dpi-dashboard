# Feeding the dashboard

There are three ways to get data in. Pick whichever fits how your systems
already work — the dashboard cannot tell the difference once the data arrives.

| | Who initiates | Good when | Config |
|---|---|---|---|
| **Pull** | The dashboard, on a timer | You already expose an HTTP endpoint with the numbers | `sources.yaml`, no code |
| **Push** | Your collector | Your systems are on a private network, or you already run a collector | `sources.yaml` + a shipper you write |
| **Seed** | Nobody | You are evaluating, developing, or taking screenshots | Default |

Every deployment starts on **seed**, so a fresh install renders a full dashboard
before you have integrated anything. That demo is generated in memory from
[`seed-catalogue.yaml`](seed-catalogue.yaml) — 178 services across ten
categories, ninety days of history, and at least one service in each of the five
states.

## The two wire formats, side by side

The files below describe **the same six services** in each format, so you can
read them against each other and decide which path to take. They are excerpts —
six services with a fortnight of history — because their job is to be read.

- [`upstream/services.json`](upstream/services.json) — what a **pull** endpoint serves
- [`push/payload.json`](push/payload.json) — what a **push** collector sends

Both are regenerated by `make seed` and are committed, so they are always in step
with the code that reads them.

### The excerpt is chosen, not sampled

It contains one service of each status on purpose. The awkward parts of the
contract only show up on the unusual services:

- the service with `"uptimePct": null` is the only one demonstrating that an
  **absent reading is not zero** — report `null`, never `0`, when you do not
  know. A zero says the service is completely down.
- the service carrying a `maintenance` object is the only one showing how a
  planned window is expressed.

Those two are what integrations get wrong most often, which is why the example
insists on including them.

## Pull

The example upstream is deliberately **not** shaped like the dashboard's own
data. It reports ratios instead of percentages, `IDENTITY` instead of
`cat.identity`, `succeeded` instead of `success`, and an age in seconds instead
of a timestamp — because a real API you already run will not match either. Every
one of those differences is something the mapping has to handle, which is what
makes it a worked example rather than an identity function:

```jsonc
{
  "data": {
    "services": [{
      "serviceId": "aadhaar",
      "displayName": "Aadhaar",
      "category": "IDENTITY",              // -> enumMap onto cat.identity
      "region": "NATIONAL",                // -> enumMap onto reg.national
      "sla": {
        "uptimePct": 0.9992,               // -> ratioToPercent, becomes 99.92
        "errorPct": 0.0062                 // -> ratioToPercent, becomes 0.62
      },
      "latency":  { "p50Ms": 264 },
      "requests": { "total": 2480492, "succeeded": 2465112 },
      "observedAgeSecs": 195,              // -> staleSeconds
      "daily": [                           // -> the history block
        { "ts": "2026-04-29", "uptime": 0.9989, "errPct": 0.0055, "count": 2088317 }
      ]
    }]
  }
}
```

To integrate your own service, change the URL in `config/sources.yaml` and edit
the `map:` block to match your field names. No Go code changes.

**You do not have to supply `daily`.** If you omit it, the dashboard rolls up its
own daily buckets from successive polls; the charts fill in over the first few
days rather than being complete immediately. Supply it if you already have the
history and want the charts populated from the first request.

### Trying a mapping before you deploy it

The dashboard polls you, so there is nothing to send it, and until the mapping is
in `sources.yaml` and the process has restarted there is nothing to look at
either. `POST /api/v1/pull/preview` closes that loop: send the document your API
would serve plus the mapping you are considering, and get back what the dashboard
would make of it — including the status it would derive.

```sh
curl -X POST http://localhost:8080/api/v1/pull/preview \
  -H "Content-Type: application/json" \
  --data '{
    "document": [ { "svc": "aadhaar", "up": 0.9992 } ],
    "mapping": {
      "map": { "id": "$.svc", "metrics.availability": "$.up" },
      "transform": { "metrics.availability": [ { "fn": "ratioToPercent" } ] }
    }
  }'
```

The `mapping` object is the same structure this file describes, key for key, so
it moves between the two by copy and paste. Drop the `ratioToPercent` and the
mapping still reads every field it was asked to — and every service comes back a
major outage, which is the mistake this exists to make visible. Records the
mapping could not read appear under `skipped` with a reason rather than
disappearing.

Nothing is fetched: the document is in the body, so the endpoint cannot be used
to make the dashboard issue requests from inside its own network.

## Push

`POST /api/v1/ingest` with a bearer token. The body is described by
[`api/dpi/v1/ingest.proto`](../api/dpi/v1/ingest.proto), and you can send it as
either JSON or binary protobuf — the endpoint decides from `Content-Type`.

**You do not need protobuf tooling.** A shell script and `curl` are enough:

```sh
curl -X POST http://localhost:8080/api/v1/ingest \
  -H "Authorization: Bearer $INGEST_TOKEN" \
  -H "Content-Type: application/json" \
  --data @examples/push/payload.json
```

`make demo-push` runs exactly that against a locally running dashboard.

The proto exists so that the contract is versioned and machine-checkable, and so
teams who want a generated client in Go, Java or Python can have one. It is not
an obligation.

### What you report, and what the dashboard decides

`IngestService` is deliberately a smaller message than the `Service` the read API
returns. It has no field for `status`, `trends` or `rankMovement`, because those
are not yours to report:

> **You report observations. The dashboard decides verdicts.**

Status is always recomputed from your metrics against the thresholds published in
`config/domain.yaml`, so the rule shown on screen is provably the rule that was
applied. If you send a service with 97% availability, it will be shown as a major
outage whatever you might have preferred to call it — and the interface will tell
the reader exactly which threshold it crossed.

### Modes

- `INGEST_MODE_UPSERT` (the default) merges the services named in the payload and
  leaves everything else alone. Use it for partial or per-service updates.
- `INGEST_MODE_REPLACE` treats the payload as the complete set, dropping anything
  absent from it. Use it when one collector owns the whole picture.

## Which fields actually matter

Only `id` is required. Everything else is optional, and the dashboard degrades
honestly rather than inventing values:

| If you omit | You get |
|---|---|
| `metrics.availability` | Status `unknown` — "we cannot tell", not "it is down" |
| `history` | Charts that fill in over the following days from local rollup |
| `incidents` | An empty incidents tab, rather than a missing one |
| `errors` | No error breakdown; the other tabs are unaffected |
| `observedAt` | The server's receipt time |

`categoryId`, `regionId`, `providerId` and `scope` must match ids declared in
your `config/domain.yaml`. Anything unrecognised is reported at startup with the
file and line, rather than silently producing a service that no filter can reach.

## Reading it back

`GET /api/v1/services` returns everything the dashboard holds, in the same wire
format, with the derived fields alongside what you sent.

## The whole surface, executable

Both of the above — and the pages, the probes and the example upstream — are
described by [`api/openapi.json`](../api/openapi.json), which is generated from
the wire contracts and checked by `make drift`. Every deployment renders it at
**`/api`** with each request editable and sendable against itself, so the
comparison this file makes in prose can be made by running both.

The examples on this page are the ones in that document, and the document reads
them from the fixtures beside it — so an example that stopped working would fail
the build rather than mislead a reader.
